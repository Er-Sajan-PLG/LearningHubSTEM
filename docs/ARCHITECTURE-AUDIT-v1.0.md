### 1.2 Specified vs. implemented (the honest ledger)

**Specified but NOT implemented**
- ADR-0016 orders entity fields `updated_at, version, external_ids, rights` — **none exist in `concept.schema.json`** (verified: zero matches). Connection-side ADR-0016 fields were implemented; entity-side were silently dropped.
- ADR-0014: "Validator enforces mutual exclusivity" of `assertion.type` vs `inference` block — **no inference check exists anywhere in `validate.py`** (grep: zero hits). The schema has an `inference` object but no conditional constraint.
- ADR-0013: "Validator warns if `confidence` set without `confidence_basis` and vice versa" — the warning lives only in a *report script* (`integrity_anomalies.py`), not the gate; `validate.py` has zero confidence logic.
- ADR-0016's derived `integrity.claim_signature` / `content_hash` — **implemented nowhere** (no export contains them).
- Controlled vocabularies `domains.yaml` / `subdomains.yaml` / `regimes.yaml` are declared "controlled per ADR-011/0012" and "validated against this file" — **no script references them** (grep: zero hits). Measured consequences: **194/654 connections carry `(domain, subdomain)` pairs that violate the subdomain vocabulary**; 142 connections use `context.domain: math` while the domain vocabulary and entity `domain` field say `mathematics`; one connection uses `scale: microscopic`, which is not in the scales vocabulary.
- Specification §2: "Entity files live directly under `content/` (no subdirectories in v0.1)" — reality is a 3-level tree. The spec was never updated (the internal plan admits this as R6).
- Specification §5.1 ten-relation whitelist is still what `validate.py` enforces for *inline* relationships (`REL_TYPES`), while the authoritative registry has 50 relations. Inline and connection vocabularies have diverged inside the single gate.

**Implemented but NOT specified**
- The entire `exports/knowledge.{all,canonical,extended,proposed,rejected,reviewed,trusted}.json` family and the `graph_policy` trust policies — none of these derived views are in the export contract (§11) or any ADR; consumers have no spec for them.
- `verify_all.py` as the CI entry point, the review state machine (`curation_state.py`, `review.py`), the whole ingestion/curation pipeline — implemented beyond spec v0.1 text, described only partially in `docs/INGESTION.md` and the (unratified) implementation plan.
- Entity `extensions.dimensions` / `symbol_set` (ADR-0017 mechanism) — used on exactly **1 entity**, with semantics (a *law* carrying `M L T^-2` dimensions) that are type-inconsistent (dimensions belong to quantities).
- Explorer auto-sync inside `validate.py` — the validator writing into a consumer app directory is nowhere specified as a gate responsibility.

**Partially implemented**
- First-class connection model (ADR-0011): schema, registry, validation, and export all exist — but the **inline `relationships[]` projection is still canonical-shaped, still schema-required-by-omission, still consumed** (explorer and the LearningHub adapter read it), and there is no generator or consistency gate between the two representations. Measured today: **all 641 inline relationships are duplicated 1:1 as connection files**; 6 connection pairs exist *only* in connections. Two sources of truth, by measurement, not just by worry.
- Relation registry semantics: `family`/`transitive`/`symmetric`/`domain`/`range` are declared and domain/range is enforced — but **39 inverse-coherence defects** exist (see Phase 7) and transitivity/symmetry are never machine-checked anywhere.
- Provenance: rich on connections (asserted_by/generated_by/method/reviewed_by/review_history/evidence[]), thin-to-stringly on entities (single `provenance` object; `source` is a free-text string on 149 entities — including **curriculum bodies** like "NCTM Principles and Standards / ICSE Mathematics Curriculum", which sits badly against the "no curriculum in canonical" invariant).
- Three-track versioning: schema/export/content tracks exist on paper; in fact `schema_version`/`export_version` are hardcoded `"0.1"` while schemas self-describe v0.2, `VERSION` says `1.0.0`, there are **no git tags/releases**, and the tracked export churns on every validator run because `generated_at` is a wall-clock timestamp (verified: my read-only validation run dirtied 3 tracked files).

**Implemented inconsistently**
- `context.regime` was stamped `["classical"]` by migration on **650 of 654 connections** — including photosynthesis bridges and DNA↔covalent-bond edges. This is fabricated uniformity masquerading as epistemic context, and it directly contradicts ADR-0013's "migration never fabricates" principle.
- Domain naming: entities `mathematics`, connections `math`; ID prefix `math`; directory `math`.
- Agent identity: 641 connections say `asserted_by: {type: unknown}` — the provenance system's central field is "unknown" for 98% of the graph.
- Filenames embed `:` (`lhs:conn.000001.yaml`) — illegal on Windows checkouts, a real defect for an "open foundation" (already ticketed internally as R11, still unfixed).

## Phase 2 — What STEMMA actually is

**Classification:** STEMMA is a **schema-driven, file-based canonical knowledge repository with a reified typed-assertion graph** — i.e., a *statement-level knowledge graph under construction*, with governance and provenance machinery around it. Concretely:

- Not an ontology: there is no formal semantics, no reasoner, no axioms beyond domain/range lists; the "registry" is a controlled vocabulary with flags, not a logic.
- Not (yet) a knowledge graph in the operational sense: the graph exists as 654 YAML files, but its consumers (explorer, the sole product adapter) actually traverse the **legacy inline projection**, and 92% of its edges carry no human authority.
- Not a schema-first knowledge base in the strict sense: schemas validate, but the entity "schema" is a broad envelope (one shape for 5 used types) while per-type semantics live in prose.
- Closest production analogues: **Wikidata's statement model** (claim + qualifiers + references + ranks ≈ connection + context + evidence + review/lifecycle) and **Biolink Model's Association pattern** — both of which ADR-0011 explicitly borrowed. This is the right neighborhood.

If forced onto the prompt's menu: *schema-driven knowledge base + reified property-graph-style assertion layer, pre-emerging into a knowledge graph*. The documentation claims "active canonical foundation" — by the project's own definition (canonicality is a governed property, not a folder), **there is currently no canonical knowledge in STEMMA at all**: every entity is `draft`; only 50 assertions have passed a (pseudonymous, unauditable) human gate.

## Phase 3 — SOTA comparison (September 2026)

Standards verified against primary sources: RDF 1.2 (triple terms / `rdf:reifies`) and SPARQL 1.2 remain **W3C Working Drafts** as of July–August 2026; JSON-LD 1.2 was chartered in January 2026 with expected completion **Q4 2027** (JSON-LD 1.1 is the current Rec); MathML Core reached **Candidate Recommendation in June 2025**; MCP was donated to the Linux Foundation's Agentic AI Foundation in December 2025 and is the de-facto agent-tool protocol (~97M monthly SDK downloads, 10k+ public servers); Wikidata holds ~1.65B statements across 120M+ entities under CC0 with statement-level ranks and references.

| Approach | Verdict for STEMMA's actual goal |
|---|---|
| **RDF / RDFS** | Not required canonically. At 224 entities / 654 assertions, a triple store adds operational cost with zero correctness gain. Keep as a **derived projection** (D6.3 already plans this). |
| **RDF-star / RDF 1.2 triple terms** | The canonical formalization of exactly what STEMMA's connection objects do (statements about statements, without asserting them). Since it is still a WD, betting the canonical layer on it now would be premature — but STEMMA's connection model is *forward-compatible* with it: `{source, relation, target}` ≈ triple term; `assertion/context/evidence/provenance` ≈ annotations on the reifier. This is a **design win to preserve**; keep the mapping trivial. |
| **OWL** | Wrong tool. STEM knowledge *pedagogy* needs open-world flexibility and human-governed disagreement, not entailment over a 654-edge graph..owl pays off for classification-heavy ontologies (ChEBI, GO). STEMMA has ~1 hierarchy in use. Defer for years. |
| **SHACL** | Not needed at the authoring gate (JSON Schema + custom checks suffice and are already built). Worth adopting **only as the validation vocabulary for the RDF/JSON-LD projection**, so external consumers can validate STEMMA data with standard tooling. Do not re-implement the validator in SHACL. |
| **SKOS** | Right ideas, partially duplicated: `broader_than`/`narrower_than` re-invent `skos:broader/narrower` *and* duplicate `generalizes`/`special_case_of` (see Phase 5). Map to SKOS in the projection; prune the internal duplication. |
| **JSON-LD** | The correct **export/interop** format: STEMMA's export is already JSON; a `@context` mapping `lhs:` relations to IRIs is cheap and gives RDF round-tripping without changing authoring. Adopt as derived projection when publishing (2026 status: 1.1 Rec, 1.2 in flight). |
| **Property graphs** | STEMMA *is* a property graph with reified edges, stored as files. Correct. A graph database is a **derived index**, not the canonical store, at this scale. |
| **Wikibase/Wikidata** | The strongest single precedent. Steal three things STEMMA lacks: (1) **statement ranks** (preferred/normal/deprecated) for competing claims instead of only `related/contradicts` relations; (2) **external-ID properties** (STEMMA has none — `external_ids` was specified in ADR-0016 and never implemented); (3) CC0-level clarity on data licensing per statement. Do **not** adopt Wikibase software: its canonical store is a wiki+SQL stack optimized for crowd editing, not governed curation. |
| **Biolink Model** | The closest schema pattern for qualified associations (association → subject/predicate/object + qualifiers + evidence + provided_by). The connection model is already a lightweight Biolink. Map relation families → Biolink predicates in the projection; don't import the whole 2,000-term model. |
| **PROV-O / nanopublications** | Connection provenance is a competent PROV-lite (agent/activity separation per ADR-0015). Nanopublication (assertion+provenance+pubinfo, signed, content-addressed) is the right long-term *publication* unit for connections; adopt the pattern, not necessarily the tooling, when publishing. |
| **Relational knowledge models** | A SQLite/Postgres mirror is a fine *derived* query layer (SQL joins over entities/connections are trivially derivable). Not canonical. |
| **Versioned knowledge architectures** | Git + immutable IDs + deprecation pointers is sound and standard (it is, functionally, what Wikidata dump history and datomic-style immutability approximate). Missing pieces are procedural (tags, hashes), not architectural — see Phase 9. |
| **AI-native representations / GraphRAG-style architectures** | 2025–2026 practice converged on: curated structured knowledge + deterministic retrievers + LLM consumers, with embeddings **derived**. STEMMA's canonical→derived doctrine matches the SOTA pattern exactly (see Phase 11). |
| **Embeddings in the canonical layer** | **Never.** They are model-versioned, lossy, derived functions of text. STEMMA's own governance already says this; hold the line. |

**Net:** STEMMA's core bets (Markdown+YAML canonical, file-per-assertion, registry-governed relations, provenance-first, derived-everything-else) are *aligned with 2026 SOTA practice*, and deliberately avoid the two classic failure modes: premature RDF adoption and premature infrastructure. The gaps are not "wrong stack" — they are **unfinished enforcement, incoherent vocabulary machinery, and a hollow STEM-representation layer**.

## Phase 4 — Canonical vs derived

The declared pipeline (canonical → validation/versioning/governance → derived projections → retrieval/embeddings/AI context → applications) is **genuinely SOTA** — it is the same shape as Wikidata (wikibase core → dumps/WDQS/Elastic → clients), and it correctly refuses the modern anti-pattern of letting a vector store or an LLM's paraphrase become the record.

But today the boundary is **violated in both directions**:

1. *Upward violation (derived leaking into canonical):* the inline `relationships[]` block — explicitly demoted to "compatibility projection" by ADR-0011 — is still hand-maintained canonical data, still in `concept.schema.json`, still exported as the relationship source. The projection is ahead of or behind the canonical graph depending on file (6 pairs connections-only; zero generator; zero consistency gate). There are two truths.
2. *Downward violation (canonical doing derived work):* `validate.py` writes the explorer's copy; `graph_analysis.py` derives centrality/PageRank; the "extended" export embeds inverse edges and transitive closures with per-edge derivation paths — all correct as *derived* artifacts, but they are tracked in git next to canonical data with wall-clock timestamps, so freshness can't be verified and diffs are noise.

**What MUST be canonical (and only this):**
- Entities (identity, definition, type, domain, lifecycle, deprecation pointers).
- Assertions (connections) with their epistemic metadata — the **only** place relationship truth lives.
- Sources (citation records), the relation registry, controlled vocabularies, schemas, and the decision records (governance IS canon).
- Historical attribution where it is a fact about the claim (who stated it, when).

**What SHOULD be derived:** every export flavor; inverse edges; transitive/prerequisite closures; connectivity/centrality analytics; JSON-LD/RDF/SKOS/schema.org projections; search indexes; embeddings; MCP/tool responses; curriculum crosswalks (consumer-owned); the explorer's data; API responses; LLM context packs.

**What MUST NEVER become canonical:** embeddings and vector indexes (model-relative, lossy, unverifiable); LLM summaries/paraphrases (authority-laundering); RAG chunks (a retrieval convenience); cached graph representations (regenerable); search indexes; *consumer* artifacts — curriculum mappings, lesson plans, products; and **derived relation forms written back into entity files** (the current inline projection, once connections are the single truth).

## Phase 5 — Canonical object model

The six-type enum (concept, quantity, unit, law, equation, misconception) is **documented but not lived**: `misconception` has zero instances (yet 220/224 entities carry `common_misconceptions` *string lists* — the type and the field are rival representations of the same idea); `equation` has 2 instances that are prose concepts ("equations of motion"), not formal objects; `unit` has exactly 1 instance — a generic essay on what a unit is, **not one actual unit**. Meanwhile the relation registry's domain/range references four types that **cannot exist** (`phenomenon`, `model`, `experiment`, and even `regime` — which is a vocabulary value, not an entity type at all, making `limited_by`'s range unsatisfiable). This is the single clearest signal that the object model and the relationship model were designed in different rooms.

**Missing primitives (needed for STEM as a domain, in priority order):**
1. **`phenomenon` and `model`** — the registry already assumes them; causal/explanatory/model families (33 relations) are un-usable or type-checked against phantoms until they exist. This is R20 in the internal plan; it is correct and should be an ADR now.
2. **`experiment` / `procedure`** — `key_experiments` string lists exist on 190+ entities; evidence types reference `experiment`; the measurement family (`measures`/`measured_by`) has range `experiment`. Today "the Cavendish experiment" is a string. Even a minimal `process`/`activity` type would serve experiments, procedures, and methods.
3. **`substance` / `material` (or entity-typed elements/compounds)** — chemistry content (40 entities) models `compound`, `acid`, `atom` as bare `concept`s; there is no way to say water *is a* substance with formula H₂O, molar mass, density. This caps chemistry fidelity at encyclopedia-text level.
4. **`assumption` as referenceable object** — assumptions are strings inside connection contexts; a derivation chain cannot cite an assumption stably (M13 in the metadata matrix defers this; fine to defer *ontology*, but reserve the ID space).
5. **`agent`/`person`** — `historical.stated_by: "Isaac Newton"` is an untyped string; `provenance.reviewer` is a pseudonymous string (`human:reviewer.biology-001`). No person can be linked, deduplicated, or credited across 10–20 years of contributions. (Agents deserve lightweight registry objects, not full biographies.)
6. **`derivation`/`proof` object** — the deepest STEM gap: nothing can represent *how* an equation follows from principles (see Phase 10).

**Unnecessary / wrong abstractions:**
- **Four part-whole relation pairs** (`part_of/has_part`, `contains/contained_in`, `composed_of/composes`, plus `appears_in_law` accidentally inverse-paired with `contains`) and **two hierarchy pairs** (`generalizes/special_case_of` *and* `broader_than/narrower_than`) and **five dependency relations** (`requires`, `prerequisite_of`, `mathematically_requires`, `logically_requires`, `depends_on`) with near-identical semantics. 37 of 50 registry relations have **never been used**. The vocabulary is speculative ontology — exactly what the project's own "build small" doctrine forbids.
- **`unit: "metre per second squared (m/s²)"`** — a display string carrying name+symbol in one field, unparseable, unconvertible, un-validatable. This is the wrong abstraction for a canonical layer (fix in Phase 10).
- **`equation` as a free string that can hold two formulas separated by `|`** (`ax² + bx + c = 0 | x = (-b ± √(b²-4ac))/2a`) — unparseable display text occupying the canonical slot where structured math should live.
- **`common_misconceptions` strings vs `misconception` entities** — pick one (recommend: entities, linked by a `misconception_of` relation, so misconceptions themselves become queryable, sourced, reviewable objects).
- **`learning_objectives`** — "Calculate acceleration from change in velocity and time" is an assessment objective. It is the closest thing to pedagogy inside canonical entities and contradicts the Knowledge≠Pedagogy wall in spirit. Move to consumer layer or quarantine in `extensions`.

**Objects that should be relationships/assertions:** `common_misconceptions` (→ misconception entities + relation); `key_experiments` (→ experiment entities + `established_by`); `real_world_applications` (→ `applied_in`/`enables` assertions); `equation`/`symbol`/`unit`/`dimensions` on entities (→ typed, provenance-bearing statements — see Phase 10). The general principle, which STEMMA has already accepted for relationships but not for entity fields: **if a statement can be wrong, contested, or sourced, it deserves assertion-shaped storage.**

## Phase 6 — Identity

**Current state (verified):** `lhs:<domain>.<slug>` human-readable IDs, regex-validated, never reused (enforced by `check_id_immutability.py` over git history — a genuinely good CI guard); `lhs:conn.NNNNNN` sequential opaque IDs; `lhs:src.<slug>`; agent namespaces `human:/llm:/process:/unknown:`; `aliases` for historical IDs; `deprecated_by` for merge/split; no external identifiers anywhere; schema `$id`s are placeholders (`learninghubstem.example`); **connection identity (source/relation/target) has no immutability guard** (a migrated connection can silently be re-pointed); reviewer identity is pseudonymous and policy-undefined.

**What's right:** never-reuse, deprecation-not-deletion, rename≠reidentify, and the git-history enforcement. This is better discipline than most academic KG projects ever achieve.

**What will not survive 10–20 years:**
1. **No global namespace.** `lhs:phys.force` is only meaningful inside this repo. An "open foundation" whose IDs cannot be cited on the web, in a dataset, or by an agent without private context is not yet open. The fix is cheap and known: mint permanent HTTPS URIs (w3id.org or owned domain — `https://stemma.<domain>/id/phys.force`), keep `lhs:` as the compact lexical form, publish a redirection spec, and set real `$id`s.
2. **No external anchor IDs.** For interoperability and entity resolution, every entity/source/agent should be able to carry `external_ids` (Wikidata QID, ORCID for humans, DOI/ISBN for sources, QUDT/UCUM codes for units, CAS numbers for substances). ADR-0016 specified this; it was never implemented; it is the cheapest high-value identity work available.
3. **Sequential 6-digit connection IDs** (`conn.000001`) will collide operationally with concurrent contribution at modest scale (merge conflicts, ID races). They are fine as file keys but should be backed by content-derived or ULID/UUIDv7 identity so two independent proposals of the same claim can be detected as duplicates (claim signature = hash(source|relation|target|polarity|qualifiers) — specified in ADR-0016, never implemented).
4. **No split/merge tooling or registry.** The lifecycle table exists in prose; there is no operational path (which aliases get minted, how evidence transfers, who approves). At 10× the size this becomes the daily bread.
5. **Reviewer identity pseudonyms** (`human:reviewer.physics-001`) are unauditable — provenance claims that cannot be attributed to a persistent, verifiable identity (ideally ORCID) will not earn trust from the scientific community this project courts.

**Recommended identity model:** HTTPS URI = canonical identity; `lhs:` slug = local name; `version` = content hash (not a counter); `external_ids` = first-class, multi-valued, namespaced (wd:Q…, doi:…, orcid:…, qudt:…, ucum:…); connection identity = claim-signature (semantic) + opaque ID (record); deprecated IDs reserved forever + `aliases` + `deprecated_by` (keep); agents get registry entries with class + persistent external ID; publish a `/id/` redirect service when the foundation goes public.

## Phase 7 — Relationships and graph semantics

The **registry design is the right architecture** (name → family, inverse/symmetric, transitive, domain/range; inverses derived, never stored — SKOS/Wikidata pattern). The **implementation is defective**. Programmatic verification found **39 inverse-coherence defects**:

- **35 relations declare inverses that are not defined in the registry** (`requires→required_by`, `causes→caused_by`, `explains→explained_by`, …). The derived-graph engine (`graph_analysis.py`) therefore emits inverse edges whose `relation` names are **not legal relations** anywhere. The derived vocabulary escapes the controlled vocabulary — a direct contradiction of ADR-0012 ("registry is the single source of truth").
- **`appears_in_law` declares `inverse: contains`**, but `contains` is a structural relation whose own inverse is `contained_in`, and the domain/range sets of the pair are incompatible. One relation, two contradictory inverses.
- **`part_of`/`has_part` have asymmetric domain/range sets**, so an edge legal in one direction has no legal inverse representation.
- `corresponds_to` declares `inverse: corresponds_to` (self) while also being `symmetric` — cosmetic, but symptomatic.

Additionally: **no machine check exists for symmetry, transitivity, or cycle-freedom.** `graph_analysis.py` contains the comment "Cycle detection already in validator" — the validator contains no cycle detection (grep-verified). I checked the current data: zero dependency and hierarchy cycles today, but nothing would catch the first one, and ADR-0012 promises dependency-cycle detection as a designed guardrail.

**Vocabulary reality check:** 12 of 50 relations are used; `related_to` alone is 371/654 (56.7%). The classifier that proposes upgrades from `related_to` to `bridges` (36 proposals) is a good, conservative pattern — but the deeper problem is that the epistemic payload ("in what sense related?") is precisely what `related_to` discards.

**Does STEMMA need RDF, property graph, reified assertions, or statement objects?**
- **Reified assertions: yes — already chosen, correctly** (connection objects). This is the only model that natively carries qualifiers, evidence, polarity, lifecycle, and per-assertion provenance; it is what Wikidata statements, Biolink Associations, and RDF 1.2 triple terms all converge on. Keep it; finish it (single source of truth).
- **Property graph semantics: yes as a *projection*.** Consumers should get a graph API/index derived from connections; the canonical layer should stay record-oriented (files), which survives tool churn.
- **RDF: as a derived export only** (JSON-LD with a `@context`; triple terms when RDF 1.2 Rec lands and tooling exists). The n-ary/contextual needs (regimes, assumptions, qualifiers, evidence stances) would each require reification gymnastics in RDF today — STEMMA's objects already model them more directly.
- **What's genuinely missing semantically:** (a) **statement ranks for competing claims** — today contradiction is a *relation* (`contradicts`) between entities, but the common STEM case is *two assertions between the same pair with different regimes/evidence*, which the connection model supports structurally but nothing ranks or reconciles (Wikidata's preferred/normal/deprecated ranks are the proven answer — adopt an equivalent `rank` on assertions or derive it from confidence+review); (b) **temporal validity is schema-only** — `validity{}` exists, zero uses, no enforcement or convention; (c) **contextual identity of claims** — the claim signature (Phase 6) is prerequisite for "same assertion, different context" reasoning and duplicate detection, and doesn't exist.

## Phase 8 — Provenance and epistemic model

**Connections: strong by design, hollow by data.** The connection schema implements a credible PROV-lite: `asserted_by`/`generated_by`/`method`/`reviewed_by`/`review_history[]` (with timestamps and reasons), `evidence[]` (typed, stanced, source-referenced, locatable), `confidence`+`confidence_basis`, `polarity`. In practice: `asserted_by: unknown` on 641/654; 599 connections have zero evidence; the only confidence value in the corpus is one hand-set 0.99; evidence stances are 56× `supports` and nothing else (no `contradicts`/`qualifies` evidence exists anywhere); the entire evidence apparatus points at **3 skeleton source records**.

**Entities: weak.** One `provenance` object per entity (`ai_drafted`, `source_kind`, `source` free string, `reviewer`, `reviewed_at`). Property-level provenance does not exist: nothing records *which source supports the definition* vs *which supports the equation* vs *which supports the examples*. The `historical` field (ADR-0018) is a genuinely good, rarely-seen distinction (record source vs. claim origin), but `stated_by` is a string and contested-origin handling is a note field.

**Missing before this becomes debt (add now, cheap):**
1. **Property-level provenance for high-stakes entity fields only** (`definition`, `equation`, `unit`): either mini-assertion objects or a per-field `source_ref` convention. Do not build a full quads layer; do it for the fields consumers will litigate.
2. **Evidence stance diversity + disagreement modeling:** the machinery for competing claims exists (multiple connections, `contradicts`, stance) but there is no *rank/resolution* semantics: if two `causes` assertions disagree, which wins for a consumer? Adopt Wikidata-style ranks (or document "all active assertions are equally exposed; consumers filter by review+confidence") as a written rule.
3. **Supersession/deprecation as first-class flows with validators:** entity `deprecated` requires `deprecated_by` (enforced); connection `deprecated/superseded` + `lifecycle.replaced_by` exists in schema but has **zero instances and no validator rule** that `replaced_by` resolves (dangling-pointer class bug waiting).
4. **Agent registry:** `human:reviewer.biology-001`, `process:migration.relationships-v0.2`, `unknown:legacy-relationship` are strings with no home. A tiny `agents/` registry (id, class, external_id, display name) turns provenance from decoration into accountability.
5. **Computed/inferred knowledge:** the `inference{rule, path}` block is right-shaped (and unimplemented in the gate). Add the validator rule (ADR-0014) before any inference is ever stored, or the first inferred edge will be indistinguishable from an asserted one.

**Granularity verdict:** object-level for entities + assertion-level for relationships is the correct target; property-level provenance is needed *only* for math/unit/definition fields; claim-level provenance already exists (connections) and should remain the crown jewel — every effort should move *toward* "everything important is a connection."

## Phase 9 — Versioning

**Present:** git for history; three declared version tracks (schema / export contract / content); `VERSION` file; immutable IDs with git-history enforcement; forward-only lifecycle in prose.

**Defects (all verified):**
1. **The tracks disagree with each other and with reality:** `schema_version`/`export_version` hardcoded `"0.1"`; schemas self-describe v0.2; `VERSION` = `1.0.0`; no tags or releases exist. Four version signals, no single truth — a consumer literally cannot state what it consumed.
2. **No content-release mechanism.** The most important version for knowledge — "the corpus as of date X, hash Y" — does not exist. No tags, no release notes, no content manifests, no hashes. Reproducibility is currently "whatever main was when you cloned."
3. **Non-deterministic derived artifacts:** `generated_at` wall-clock means every validator run dirties git (I caused three file modifications with a read-only audit). A tracked derived artifact that can never be `git diff --exit-code`-clean is a process defect.
4. **Object immutability unenforced where it matters most:** entity content hashes don't exist (a "released" entity could be silently edited — nothing mechanical enforces "released entities are never edited in place"); connection triples have no immutability guard (R12); only IDs are protected.
5. **No migration tooling discipline:** schema evolution so far was ad-hoc (v0.1→v0.2 additive fields, plus the unimplemented entity-side ADR-0016 fields). No schema migration tests, no "old data validates against old schema" harness, no deprecation windows.

**Git-based vs event-sourced:** **Git is correct for this project** at any scale it will plausibly reach in five years (Wikidata-scale would be different). Event sourcing adds machinery whose benefits (audit, time travel) git already provides via commits + tags. What to add, in order: (1) deterministic exports (content-hash stamp instead of `generated_at`) + CI freshness gate; (2) git tags + content manifest (file hashes) as immutable content releases; (3) object `content_hash` + edit-in-place detection for human_reviewed/canonical objects; (4) documented branching convention (proposals via PR, canonicalizations squash-merged with reviewer recorded); (5) a migrations log file. Branching/merging *of knowledge* (as opposed to code) should remain ordinary git flow — do not invent a semantic merge layer.

## Phase 10 — STEM-specific representation

**This is the weakest layer of the entire system.** Measured:

- Equations: free display strings, including multi-formula strings (`F = dp/dt (general); F = m·a at constant mass`; `ax² + bx + c = 0  |  x = (-b ± √(b² - 4ac)) / 2a`). Not parseable, not type-checkable, not symbol-bound.
- Symbols: `symbol: a` (string) or `symbol_set: "F, m, a, p, t"` (one string, comma-split by hope). No symbol→quantity binding anywhere. Two entities using `a` for different things cannot be disambiguated.
- Units: `unit: "metre per second squared (m/s²)"` — name and symbol in one string. No unit entities (one essay-entity about units exists), no conversions, no UCUM/QUDT codes, no unit arithmetic.
- Dimensions: `extensions.dimensions: "M L T^-2"` — a string in a bespoke notation, present on exactly one entity (a *law*, where a dimension is arguably meaningless; dimensions belong to quantities).
- Derivations: entirely absent. There is no representation for "this equation follows from these principles under these assumptions" — the epistemic core of physics. `derived_from` connections exist (3 uses) but carry no derivation content.
- Variables, constraints, boundary conditions, functions/transformations, assumptions-as-objects: absent (assumptions are string arrays; regimes/qualifiers exist structurally but are unused).

**Standards verdict:**
- **Do not** put MathML/OpenMath into the canonical authoring format — hand-writing MathML in YAML frontmatter would kill the human-writable property that is the format's best feature.
- **Do** canonize a minimal *semantic* math layer: (1) one canonical **LaTeX string** per equation (single, linted, deterministic rendering source); (2) a **symbol map** — `{symbol: "F", quantity: lhs:phys.force}` — making every variable an ID reference; (3) **dimension vectors** on quantities in a defined alphabet (MLTQΘNIJ, or QUDT's dimension vectors); (4) **unit IDs** referencing QUDT/UCUM codes via `external_ids` (QUDT is the right open reference for quantity-kind/unit/dimension; UCUM where clinical precision is needed; SI/BIPM as ground truth).
- **Derive** MathML Core (W3C CR since June 2025, browser-implemented) for rendering; derive OpenMath/ MathML-Content for semantic exchange when a consumer needs CAS interop; derive plain text for LLM contexts.
- **Validate** what is now checkable: dimensional consistency of declared equations (given symbol→quantity→dimension bindings, `F = m·a` type-checks; a wrong equation fails the gate), unit-dimension agreement (`unit` of a quantity must reduce to its `dimensions`), and duplicate-symbol conflicts within an entity. This is the single highest-leverage "canonical correctness" investment available to STEMMA — it converts the knowledge layer from prose-with-decorations into a checkable artifact.

**Canonical vs presentation:** canonical = LaTeX + symbol bindings + dimension vectors + unit references. Presentation (MathML, Unicode-pretty strings like `metre per second squared (m/s²)`, plain text) = derived. The current strings should be demoted to derived renderings.

## Phase 11 — AI-native consumption

**Direct answer to the central question: do NOT expose the canonical representation raw to AI as the primary interface — and do not hide it either.** The right architecture, which STEMMA's own doctrine already implies:

1. **Policy-graded structured APIs** (deterministic, from canonical): the `graph_policy.py` trust filters (`all / reviewed / canonical / trusted`) are exactly right — generalize them into the *contract*: every AI-facing query carries a trust floor (`review.status ≥ reviewed`, `assertion.status = active`, evidence ≥ 1). AI consumers get "what humanity here has reviewed", not "what a migration script asserted at 2am" — today those are the same 654 edges, which is precisely why the export must be policy-tagged.
2. **An MCP server as the tool interface.** In 2026 this is the standard answer (MCP: Linux Foundation/AAIF, native support in all major AI clients). Tools: `get_entity(id)`, `get_assertions(id, policy)`, `get_prerequisites(id, transitive, policy)`, `get_subgraph(ids, relations, policy)`, `get_evidence(connection)`, `search(query, filters)` — all computed from canonical data, all returning provenance and review status inline so the LLM can cite them.
3. **Deterministic context packs for RAG:** subgraph-to-text projections with per-assertion attribution lines ("[lhs:conn.000377 · canonical · evidence: Halliday Ch.5]") — machines consume structure; LLMs consume the *rendering* of the same structure. Never let the LLM's paraphrase flow back.
4. **Embeddings + lexical search: derived indexes only**, rebuilt by pipeline from the export, tagged with the embedding model version, never canonical. Hybrid retrieval (BM25 + vectors + graph expansion over `requires`/`part_of`) is the 2025–2026 SOTA pattern (GraphRAG-style traversal-constrained generation); STEMMA's prerequisite graph is exactly the kind of traversal constraint that measurably reduces hallucination in tutoring contexts.
5. **AI as authoring pipeline, not authority:** already designed correctly (ingest → draft proposals → gates → human canonicalization). Keep.

**Anti-requirements to hold:** no vector DB as canonical (governance already forbids — keep); no "let the LLM answer from its weights and record the answer"; no auto-upgrading `related_to` by embedding similarity (the repo's own classifier is deliberately non-embedding — correct).

## Phase 12 — Storage

**Verdict: Git + structured files is the correct canonical store for STEMMA — now and for the foreseeable future.** Scored against the prompt's criteria: correctness (text+schema+gates ✔), inspectability (`less` is the query tool ✔), portability (git clone = full replica ✔), openness (no server ✔), reproducibility (⚠ needs tags+hashes+deterministic exports), version control (native ✔), migration (text diffs ✔), preservation (plain text in git is the most durable format class we have ✔).

- **Not** a relational/document DB as canonical: any DB is a second runtime to preserve, backup, and trust; the repo would lose the "clone = whole truth" property for near-zero correctness gain at this scale (224 entities / 654 assertions is ~1.2 MB of JSON).
- **Not** a triple store as canonical: RDF round-trip belongs in the projection layer (Phase 3).
- **Not** a graph DB as canonical: acceptable later as a **derived query index** when consumers need interactive traversal at 10⁵+ entities; regenerable, never authoritative.
- **Object storage/CAS:** unnecessary until binary media (figures, simulations) enters the corpus; if/when it does, git-lfs or a CAS sidecar — not a new canonical home.
- **Hybrid (recommended end-state):** canonical git repo (entities, connections, sources, registries) → deterministic build → derived artifacts (JSON exports, JSON-LD, SQLite mirror, search index) published as **release assets keyed to content hashes**, not tracked files. Stop tracking `exports/` in git (or make them bit-identical under regeneration and CI-enforce it). The current practice of committing 8 regenerable JSON files + an explorer copy is the storage-layer's biggest hygiene defect.

## Phase 13 — Interoperability

**Posture (recommended): link and cite; map for export; import as evidence; never synchronize; never depend.** STEMMA should remain *independently authoritative*: its definitions, its review gates, its IDs — with external systems as **anchors and evidence**.

- **Wikidata:** attach QIDs via `external_ids` (e.g., force → Q11402) for dedup and discovery; treat Wikidata statements as *leads/evidence*, never as canonical content; do not mirror labels/descriptions.
- **QUDT / UCUM / OM:** reference unit & quantity-kind codes for every quantity/unit entity (the fix of Phase 10). This is the highest-value external mapping in the whole plan because it makes STEMMA's math machine-checkable.
- **Biolink:** map connection families → Biolink predicates in a derived JSON-LD projection so biomedical consumers can join without translation code.
- **schema.org (`DefinedTerm`) / LRMI:** the web-publication projection for definitions (already listed as future alignment in spec §14 — keep it derived).
- **SKOS / OWL:** SKOS mapping for vocabularies (`generalizes` → `skos:broader` etc.) in the same projection; OWL only if a consumer needs it, derived, lossy-by-design.
- **CASE / OpenSALT (1EdTech):** curriculum crosswalks are consumer-owned; STEMMA publishes the stable IDs to crosswalk *to* (already the doctrine; the grade-12 mapping doc correctly lives outside `content/`).
- **DBpedia:** low value in 2026; Wikidata subsumes it.
- **Synchronization:** none, ever, in the canonical direction. Re-imports happen through the gated pipeline as *proposals with provenance*, like any other draft.

## Final verdict

### Is the current STEMMA architecture fundamentally on the right trajectory?

## **YES, BUT.**

**Why yes:** the load-bearing decisions are the correct ones for a 10–20 year open knowledge foundation, and they match the strongest 2026 practice rather than fighting it: file-based canonical authoring with governed schemas; relationship truth as reified, qualified, provenance-bearing assertions (the Wikidata/Biolink/RDF-1.2 convergence point); registry-governed relation semantics; strict canonical↔derived separation with embeddings and indexes permanently derived; identity treated as an immutable contract with CI enforcement; AI positioned as a gated proposer, never an authority. This is the skeleton serious projects converge on after their first painful rebuild. STEMMA drew it first.

**Why "but":** the system currently demonstrates its principles more often than it enforces or embodies them. The two truth defects — a dual relationship model living in canonical files, and a vocabulary/provenance apparatus that is declared-controlled but machine-uncontrolled — are exactly the kinds of drift the project's own freeze-rule doctrine exists to prevent, and they are present at the semantic core. The knowledge itself is unverified end to end (zero reviewed entities; 98% of assertions of unknown origin; 3 citation skeletons; `regime: classical` stamped on photosynthesis), which means the flagship artifact — a *trustworthy* STEM knowledge foundation — does not yet exist, whatever the README says. And for STEM specifically, the canonical layer cannot yet represent the subject matter it exists for: its equations are unparseable strings, its units are prose, its dimensions are one decorative extension, and nothing is mathematically checkable. These are all fixable — most of the fixes are already sketched in the repo's own ADRs and internal review — but each month unfixed compounds, because consumers are already pinned to the legacy projection and the version signals already disagree.

**If the team does five things — (1) make connections the only relationship truth with a generated projection, (2) repair the registry and wire all vocabularies into the gate, (3) ship the math layer with dimensional validation, (4) start the human-review campaigns with real source records, (5) cut content releases with hashes and deterministic exports — STEMMA graduates from "well-designed skeleton" to the thing it claims to be: a canonical, verifiable, open STEM knowledge foundation.**
